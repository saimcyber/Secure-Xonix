2. INTRODUCTION

2.1 Project Overview
--------------------
XONIX is a modernized implementation of the classic territory conquest game 
where players control a character to capture areas of the playing field while 
avoiding enemies. The game combines strategic gameplay with modern features 
including user authentication, friend systems, multiplayer modes, and 
customizable themes.

The objective is to capture a certain percentage of the game board (70-80%) 
while avoiding enemies that move in different patterns. Players draw lines to 
create enclosed areas, which are then filled. The game features both single-
player and multiplayer modes with varying difficulty levels.

5.1 Hash Table (Friend System)
------------------------------
Implementation: FriendSystem class (FriendSystem.h/cpp)

Purpose: Efficiently manage friend relationships between players

Structure:
- Hash table size: 101 (prime number for better distribution)
- Collision resolution: Chaining with linked lists
- Hash function: Sum of ASCII values modulo table size

Justification:
Hash tables provide O(1) average case lookup time for finding players by 
username, which is crucial for:
- Quick friend request validation
- Fast friend status checking
- Efficient username-to-playerID mapping

Key Operations:
- Insert player: O(1) average
- Search player by username: O(1) average
- Send friend request: O(1) average
- Accept/reject request: O(n) where n = number of pending requests

Code Example:
```cpp
int hashFunction(const std::string& username) {
    int hash = 0;
    for (char c : username) {
        hash += static_cast<int>(c);
    }
    return hash % HASH_TABLE_SIZE;
}
```

5.2 AVL Tree (Theme Inventory)
-------------------------------
Implementation: ThemeInventory class (Inventory.h/cpp)

Purpose: Store and manage unlockable game themes in balanced binary search tree

Structure:
- Self-balancing binary search tree
- Each node contains Theme data and height
- Balance factor maintained at each node
- Rotation operations for rebalancing

Justification:
AVL tree ensures O(log n) operations for all theme operations while keeping 
themes sorted by ID. This is important for:
- Efficient theme searching during gameplay
- In-order traversal for sorted theme display
- Balanced tree prevents worst-case O(n) lookups
- Auto-balancing after insertions maintains performance

Key Operations:
- Insert theme: O(log n)
- Search theme: O(log n)
- Display all themes in order: O(n)
- Balance operations: O(log n)

Balancing Rotations:
- Left rotation
- Right rotation
- Left-Right rotation
- Right-Left rotation

Code Example:
```cpp
int getBalanceFactor(ThemeNode* node) {
    return node ? getHeight(node->left) - getHeight(node->right) : 0;
}

ThemeNode* balanceNode(ThemeNode* node) {
    int balance = getBalanceFactor(node);
    if (balance > 1 && getBalanceFactor(node->left) >= 0)
        return rotateRight(node);
    if (balance > 1 && getBalanceFactor(node->left) < 0) {
        node->left = rotateLeft(node->left);
        return rotateRight(node);
    }
    // ... other cases
}
```

5.3 Min Heap (Leaderboard)
---------------------------
Implementation: MinHeapLeaderboard class (MinHeap.h/cpp)

Purpose: Maintain top 10 players efficiently

Structure:
- Array-based binary heap
- Fixed size of 10 entries
- Root contains minimum score among top 10
- Complete binary tree property maintained

Justification:
Min heap is ideal for maintaining top-K elements because:
- O(1) access to minimum element (threshold for top 10)
- O(log n) insertion and deletion
- Easy comparison: if new score > min, replace min and heapify
- Memory efficient: fixed size array
- No need for full sorting, only maintain top 10

Key Operations:
- Insert new score: O(log 10) = O(1)
- Get minimum: O(1)
- Replace minimum: O(log 10) = O(1)
- Get sorted leaderboard: O(n log n) where n=10

Heap Property:
- Parent value ≤ Children values
- heap[i] ≤ heap[2i+1] and heap[i] ≤ heap[2i+2]

Code Example:
```cpp
void heapifyUp(int index) {
    while (index > 0) {
        int p = parent(index);
        if (heap[index].totalPoints < heap[p].totalPoints) {
            swap(index, p);
            index = p;
        } else break;
    }
}
```

5.4 Priority Queue (Matchmaking)
---------------------------------
Implementation: MatchmakingPriorityQueue class (PriorityQueue.h/cpp)

Purpose: Match players based on skill level (total points)

Structure:
- Max heap implementation (higher points = higher priority)
- Array-based heap with size 100
- Priority = player's total points

Justification:
Priority queue ensures fair matchmaking by:
- Pairing players with similar skill levels
- O(log n) enqueue and dequeue operations
- Automatic sorting by priority (points)
- Players with similar points matched first

Key Operations:
- Enqueue player: O(log n)
- Dequeue (get highest priority): O(log n)
- Peek: O(1)
- Check if matching possible: O(1)

Matching Algorithm:
1. Players join queue (enqueue)
2. When 2+ players in queue, extract top 2
3. Match them based on similar points
4. Start game

Challenge 1: Enemy Wall-Sticking and Repetitive Movement Patterns
------------------------------------------------------------------
Problem:
When enemy speed increased in higher difficulties, enemies would stick to walls
or loop in predictable rectangular patterns. This occurred because:
- Simple collision detection didn't account for high-speed movement
- Enemies could overshoot boundaries and get clamped to walls
- Bounce angles were too predictable, creating loops

Technical Details:
- At speed > 3.0, enemies moved multiple pixels per frame
- Grid-based collision detection missed intermediate positions
- Wall bounce logic always reversed direction at 90°, causing rectangles

Solution Implemented:
1. Added margin buffers (5 pixels from walls) to prevent exact wall contact
2. Increased randomization in bounce angles (±2 instead of ±1)
3. Added randomized perpendicular component to all wall bounces
4. Separated wall collision from grid collision handling
5. Capped effective speed at 5.0 with proper deltaTime handling
6. Pre-calculated positions before applying them

Code Example:
```cpp
if (newX <= margin) {
    newX = margin;
    dx = abs(dx);
    dy += (rand() % 5 - 2);  // Random perpendicular change
    dy = clamp(dy, -2, 2);
    if (dy == 0) dy = (rand() % 2 == 0) ? 1 : -1;
    hitWall = true;
}
```

Result:
✓ Enemies move smoothly at all speeds
✓ No more wall-sticking
✓ Unpredictable, natural-looking movement patterns

Challenge 2: Leaderboard Duplicate Entries and Incorrect Sorting
-----------------------------------------------------------------
Problem:
The leaderboard would show duplicate entries for the same player and wasn't 
maintaining proper top 10 ordering. Issues included:
- Multiple entries for same player after each game
- Incorrect min heap behavior
- Scores not updating, only adding new entries

Technical Details:
- insertOrUpdate() wasn't properly checking for existing players
- Heap property violated after updates
- File I/O was appending instead of overwriting

Solution Implemented:
1. Modified insertOrUpdate() to search for existing player first
2. If player exists, update their score and re-heapify
3. If player doesn't exist and heap is full, compare with minimum
4. Fixed file saving to overwrite instead of append
5. Added proper heapify operations after updates

Code Example:
```cpp
void insertOrUpdate(int playerID, const string& username, int points) {
    // Search for existing entry
    for (int i = 0; i < size; i++) {
        if (heap[i].playerID == playerID) {
            heap[i].totalPoints = points;
            heapifyDown(i);  // Re-establish heap property
            saveLeaderboard();
            return;
        }
    }
    // Add new entry logic...
}
```

Result:
✓ Each player appears only once
✓ Scores update correctly
✓ Top 10 properly maintained
✓ Correct sorting in display

Challenge 3: Multiplayer Synchronization and Control Conflicts
--------------------------------------------------------------
Problem:
In local 2-player mode, player controls would interfere with each other, and
game state wasn't properly synchronized. Issues:
- Both players could move simultaneously into same space
- Key presses from one player affected the other
- Game over detection wasn't checking both players

Technical Details:
- Single event loop processed all inputs together
- No player state separation
- Collision detection didn't account for 2 players
- Shared global variables caused state conflicts

Solution Implemented:
1. Separated player state completely (p1 and p2 structs)
2. Created individual control handlers for each player
3. Added collision detection between players
4. Implemented turn-based movement with proper timing
5. Created separate trail and capture logic per player
6. Added dual win condition checking

Code Example:
```cpp
// Player 1: WASD controls
if (event.key.code == Keyboard::W && p1_dy == 0) p1_dy = -1;
if (event.key.code == Keyboard::S && p1_dy == 0) p1_dy = 1;

// Player 2: Arrow key controls  
if (event.key.code == Keyboard::Up && p2_dy == 0) p2_dy = -1;
if (event.key.code == Keyboard::Down && p2_dy == 0) p2_dy = 1;

// Separate collision checks
checkPlayerCollision(p1_x, p1_y, &p1_alive);
```

A. Key Algorithms and Pseudocode
---------------------------------

Algorithm 1: Flood Fill (Area Capture)
```
function floodFill(y, x):
    if (y < 0 OR y >= M OR x < 0 OR x >= N):
        return
    if (grid[y][x] != 0):  // Not empty space
        return
    
    grid[y][x] = -1  // Mark as visited
    
    // Recursively fill in all 4 directions
    floodFill(y - 1, x)  // Up
    floodFill(y + 1, x)  // Down
    floodFill(y, x - 1)  // Left
    floodFill(y, x + 1)  // Right
```

Algorithm 2: AVL Tree Balancing
```
function balanceNode(node):
    balance = getBalanceFactor(node)
    
    // Left-Left case
    if (balance > 1 AND getBalanceFactor(node.left) >= 0):
        return rotateRight(node)
    
    // Left-Right case
    if (balance > 1 AND getBalanceFactor(node.left) < 0):
        node.left = rotateLeft(node.left)
        return rotateRight(node)
    
    // Right-Right case
    if (balance < -1 AND getBalanceFactor(node.right) <= 0):
        return rotateLeft(node)
    
    // Right-Left case
    if (balance < -1 AND getBalanceFactor(node.right) > 0):
        node.right = rotateRight(node.right)
        return rotateLeft(node)
    
    return node
```

Algorithm 3: Matchmaking Priority Queue
```
function matchPlayers(queue):
    if (queue.size < 2):
        return "Not enough players"
    
    player1 = queue.dequeue()  // Highest priority
    player2 = queue.dequeue()  // Second highest
    
    // Check skill difference
    skillDiff = abs(player1.points - player2.points)
    
    if (skillDiff <= THRESHOLD):
        startGame(player1, player2)
    else:
        // Re-queue and wait for better match
        queue.enqueue(player1)
        queue.enqueue(player2)
```
